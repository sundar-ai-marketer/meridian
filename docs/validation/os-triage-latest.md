## What this document is

Every advisory below has no vendor fix in the scanner database used. Debian has not published a patched version, so this fork cannot patch it either. Rebuilding the image does not clear these; only the vendor shipping a fix does.

What this fork can do is say whether the default analysis workflow touches the affected packages at all. That is measured: `scripts/container_reachability_probe.py` imports Meridian, runs real tensor work and a report-module import inside the container, then reads `/proc/self/maps` and attributes every mapped file to its dpkg package.

Measured result: **87 OS packages installed, 11 loaded** by that workflow.

Loaded packages: `libbz2-1.0`, `libc-bin`, `libc6`, `libffi8`, `libgcc-s1`, `liblzma5`, `libssl3t64`, `libstdc++6`, `libuuid1`, `libzstd1`, `zlib1g`.

## What it does not claim

- `loaded` is not a finding. Every Python process maps `libc6`. It means the package is in the process, nothing more.
- `not-loaded` is not proof of unreachability. It describes the default command only. `docker run -it meridian bash`, a mounted volume, or any other entrypoint reaches more than the probe did.
- Debian records an advisory against a **source** package and the scanner expands it across every binary package built from that source. A row naming `libuuid1` may describe a defect that lives in `mount` or `login`, which are built from the same `util-linux` source. Resolving which binary actually carries the defect requires the vendor tracker entry and is not determinable from scanner output.
- No exploitability assessment has been performed on any entry here.

## Regenerating

```
docker build --pull -t meridian:triage .
trivy image --scanners vuln --pkg-types os --ignorefile /dev/null \
    --format json --output docs/validation/container-os-latest.json \
    meridian:triage
# Copy the probe result out rather than writing through a mount: the
# container runs as uid 1000 and will not own your working tree.
docker run --name probe --entrypoint python meridian:triage \
    scripts/container_reachability_probe.py --output /tmp/probe.json
docker cp probe:/tmp/probe.json \
    docs/validation/container-reachability-latest.json
docker rm probe
python scripts/triage_container_os.py \
    --scan docs/validation/container-os-latest.json \
    --probe docs/validation/container-reachability-latest.json \
    --output docs/validation/os-triage-latest.md
```

The scheduled `container-rescan` workflow runs this weekly and opens an issue when a new fixable high or critical finding appears.
